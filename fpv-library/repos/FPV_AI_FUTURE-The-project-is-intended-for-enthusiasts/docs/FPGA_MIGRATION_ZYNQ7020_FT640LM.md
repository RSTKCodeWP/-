# Миграция ГСН на ПЛИС — Zynq-7020 (Zynq Mini) · тракт FT640LM

**Статус:** архитектурное решение v1 (2026-07-03). Кода ещё нет — это partition-документ,
фиксирующий разбиение PL/PS, тракт приёма камеры и лестницу вех. Эволюционирует.

**Цель:** перенести ядро ГСН из Python-прототипа (RPi5) в Zynq-7020, реализовав пиксельный
конвейер в фабрике (PL), а низкочастотную логику — на PS (ARM Cortex-A9). Причина —
finding №1/№9 аудита 2026-06-25: real-time мимо в 9–48× на Pi5 + железо отстаёт на подсистему.
Python-модель становится **золотым эталоном** для верификации RTL/HLS (переиспользуем
дисциплину «OFF == бит-идентично» и golden-тесты).

## 0. Железо на руках

- **Плата:** Zynq Mini, XC7Z020-CLG400, 512 МБ DDR3, HDMI-**выход**, GigE, USB Host, 34 GPIO.
  У платы **нет входа для камеры** — только HDMI на выход. Значит приём сенсора идёт через GPIO.
- **Ресурсы PL (7020):** 53k LUT, 220 DSP48, 4.9 Мбит BRAM. PS: 2× Cortex-A9 (~667 МГц), NEON/FPU.
- **Камера №1 (первая цель):** Foxeer **FT640(LM)** V2 — 640×512@60, VOx LWIR 8–14 мкм, NETD <50 мК,
  FOV 48.7°×38.6°, **выход CVBS (8-бит AGC, интерлейс). Радиометрического Y16 НЕТ.**
- **Камера №2:** тепловизор + чип «аналог→цифра» (модель пока неизвестна) — тот же аналоговый класс.
- Режим: **один сенсор за раз** на ГСН, разные камеры по очереди. Параллельные конвейеры/стерео
  НЕ требуются — нужен один камеро-агностичный конвейер + сменный front-end приёма.

## 0.5 Режим перехвата (высокоскоростной) — драйвер требований

Вводная 2026-07-03: угроза 200–300 км/ч (55–83 м/с), перехватчик 100–150 м/с. Это в 5–10× быстрее,
чем настройки старого сима (Vc ~15–23 м/с). Числа посчитаны в `fpv/guidance/engagement_regime.py`
(гейты — `fpv/guidance/tests/test_engagement_regime.py`) и жёсткие:

- **Терминал почти баллистичен.** Радиус разворота при 150 м/с и 0.84 g ≈ **2731 м** ≫ дальности
  перехвата 50–200 м. → в последние десятки метров манёвренной власти почти нет.
- **Конус упреждения узкий: <1–2°** (0.8° @100 м, 1.6° @200 м, 4° @500 м). Широкий кроссинг
  недостижим (broadside @100 м требует ~38 g). → **лид должен быть выставлен ДО терминала**
  (наземное целеуказание Блок-02 + мидкорс); ГСН лишь снимает малый остаточный λ̇.
- **Удержание трека требует предсказания.** Кроссер идёт ~10 px/кадр @60 Гц (до ~20 px/кадр @50 м)
  → ROI ставится на **предсказанную** позицию (IMM), а не на прошлую.
- **Латентность = метры промаха.** При Vc≈233 м/с 35 мс петли Pi = ~8 м «слепого» сближения;
  кроссер уходит ~2.9 м вбок. FPGA-детерминированная суб-кадровая латентность (~3 мс) → ~0.25 м.
  **Это и есть главный количественный аргумент за перенос на ПЛИС.**

**Что из этого требуется в реализации** (драйвер для вех): (1) предиктивный ROI на M1;
(2) IMM с модой координированного разворота (CT) + оживить APN — предсказание манёвра быстрой цели;
(3) FPGA-латентность как несущее требование (уже ядро); (4) аппаратная синхронизация кадр↔IMU в
фабрике (убивает доминирующую ошибку λ̇ при высоких телесных скоростях); (5) обработка смаза
(motion blur ~10 px за поле) в детекте. **Платформенная оговорка:** 100–150 м/с — это не мультиротор,
а крыло/ракетно-разгонный планер; квадрик «Архангел» столько не даёт (аудит уже отмечал runaway Vc).

## 1. Тракт приёма (критический путь)

Обе камеры аналоговые → внешний **видеодекодер CVBS→BT.656** (ADV7280 / TVP5150) в фабрику:

```
FT640LM --CVBS--> [декодер CVBS→BT.656] --8-бит BT.656, 27 МГц, sync встроен (SAV/EAV)-->
   Zynq GPIO --> RTL BT.656-RX --> de-interlace (bob, одно поле @60 Гц) --> 8-бит Y --> конвейер
```

- **Один BT.656-RX обслуживает обе камеры.** Внутренний контракт после приёма единый:
  `AXI-Stream: 8-бит Y (яркость), + tuser=start-of-frame, tlast=end-of-line, + метадата (w,h,fid,ts)`.
  Смена камеры = смена только внешнего декодера/конфига, конвейер не трогается.
- **Пины/уровни:** ~9–10 GPIO (8 data + PCLK; HSYNC/VSYNC не нужны — встроены в BT.656).
  BT.656 обычно 3.3 В LVCMOS → в пределах GPIO. Остаётся запас на I2C (конфиг декодера) + kill-линии.
- **Замена текущему пути:** сейчас FT640→MS2109(USB)→PS/Linux — латентность+джиттер (грех аудита).
  Декодер→BT.656→фабрика детерминирован и PL-нативен.

**Честные ограничения тракта (не переоценивать):**
- CVBS = **8-бит AGC, НЕ радиометрический Y16** → этот путь НЕ открывает реальный NETD/Pd-vs-дальность
  (это отдельный поздний шаг с нативной цифровой Y16-камерой).
- CVBS **интерлейсный** (NTSC 480i). Для ГСН важнее темпоральное разрешение → **bob (одно поле)
  @60 Гц**, а не weave @30 Гц. Это половинит вертикаль → см. §7 (интринсики пересчитать по реальной сетке).
- Реальная сетка на выходе декодера ≈ **720×480 интерлейс** (SD), а не «640×512». Номинальные
  `ft640_intrinsics()` (f_px≈707@640, HFOV 48.7°) надо **пересчитать под фактический пиксельный грид**
  после декодера/bob — это несущее для LOS-геометрии.

## 2. Разбиение PL / PS

| Куда | Блок | Инструмент | Заметка |
|---|---|---|---|
| **PL** | BT.656-RX + de-interlace (сменный ingest) | **hand-RTL** | протокол/тайминг-точный, маленький |
| **PL** | FFC/порог-ребейз, top-hat, адаптивный порог, CC, взвешенный центроид (`detect.py`) | **Vitis HLS** | потоковый dataflow, line-buffer; Python — эталон co-sim |
| **PL** | CFAR/MPCM/directional-median, MOSSE-FFT, MTI — **по ROI**, не полным кадром | **Vitis HLS** | оконный BRAM вокруг гейта трека (архитектура ROI из аудита) |
| **PL** | safety-интерлок: failsafe-таймер + kill AND-gate | **hand-RTL** | простой, аудируемый, детерминированный; без HLS-непрозрачности в kill-пути |
| **PL** | HDMI-overlay компоновщик (детекции/трек/телеметрия) | **hand-RTL/HLS** | «глаз ГСН» на экране для bring-up + экран оператора |
| **PS** | IMM (`imm.py`, 4 сост. @60 Гц) | **C/C++, float+NEON** | низкочастотное; float правильнее fixed-point для ковариации |
| **PS** | bearing-rate guidance, looming/τ, FSM (lock/arming/failsafe) | **C/C++** | control-flow-тяжёлое |
| **PS** | **Ed25519** авторизация, MSP-линк, конфиг камеры (I2C/SPI) | **C/C++** | крипто наконец живёт в рантайме (finding аудита) |

Побочно чинит два тяжёлых findings: kill-chain из софт-троса → железный интерлок в фабрике
(не зависит от живого Linux); Ed25519 оживает на PS.

## 3. Что 7020 потянет (грубый sizing)

Одна 8-бит SD-камера — щадящий бюджет:
- Детект-фронтенд (top-hat→порог→CC→центроид) по 720×480@60: влезает легко.
- MOSSE-FFT и MTI — тесные углы; гнать **по ROI** (~64×64 окно), не полным кадром → ~единицы DSP/BRAM.
- Полный look-down-стек полным кадром @60 одновременно — 7020 НЕ хватит; для этого ROI-архитектура
  обязательна (она и в софте так спроектирована). Если позже понадобится всё полным кадром —
  берём из имеющихся ПЛИС 7045 / Zynq UltraScale+.

## 4. Fixed-point и co-sim против эталона

- Пиксельный тракт в PL → **fixed-point** (`ap_fixed` в HLS) + анализ ошибок квантования.
  8-бит вход помогает: узкие промежуточные разрядности.
- **IMM оставить float на PS** — ковариация/NEES чувствительны, A9 имеет FPU; это правильный выбор.
- **Верификация:** Python-модуль (`detect.py`, `thermal_sim.py`, `test_flag_bit_identity.py`) —
  bit-accurate reference для Vitis HLS C/RTL co-sim. Прогоняем те же кадры (thermal_sim / записанные
  клипы) через Python и через HLS, сверяем центроид/маску. Дисциплина «golden» из аудита = актив.
- **Детект-IP можно разрабатывать БЕЗ камеры** (на записанных кадрах) параллельно с ingest-трактом;
  встречаются только на интеграции. Де-риск.

## 5. Лестница вех

- **M0 — детект-спина (hello world).** `BT.656-RX → de-interlace → HLS detect(top-hat→порог→CC→
  центроид) → AXI-Stream → PS(IMM+guidance+FSM, порт с Python) → HDMI-overlay`. Замыкает весь
  цикл PL↔PS↔верификация, даёт живой тепловой глаз ГСН на экране. Всё остальное — инкремент после.
- **M1 — трек+ROI.** Перенос lock-FSM/трекера; ROI-окно вокруг гейта; тяжёлые операторы на ROI.
- **M2 — look-down по ROI.** CFAR/MPCM/dir-median/MOSSE/MTI в фабрике, только на ROI, флаги как в софте.
- **M3 — safety в фабрике.** failsafe-таймер + kill AND-gate в PL; Ed25519 на PS; подписанный журнал.

## 6. Что докупить (BOM)

- **Модуль видеодекодера CVBS→BT.656** (ADV7280-M или TVP5150 breakout) — единственная новая железка
  для приёма. Выход 8-бит BT.656 параллель на GPIO. Проверить логический уровень (3.3 В) и I2C-адрес.
- Провода GPIO↔декодер; при желании — уровневый согласователь, если декодер 1.8 В.
