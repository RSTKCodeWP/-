## What this project is
A model-agnostic **LLM copilot for an FPV drone**, on **PX4 + MAVLink**, developed **SITL-first** (gz Harmonic). The human flies FPV manually and **delegates tasks to the assistant in natural language** (shared / hand-off control). Core safety rule: **the LLM never sits in the hard real-time control loop** — it proposes, a deterministic safety layer validates/executes, the human stays in command. Strategic context: aligned with **Baykar / TEKNOFEST** (Turkish-language + T3 AI are planned later).
- Research: `llm-flight-assistant-research.md` (+ `.pdf`)
- Design spec (authoritative): `docs/superpowers/specs/2026-06-08-llm-fpv-flight-assistant-design.md`

## Conventions & gotchas — KEEP THIS UPDATED
**Workflow:** superpowers `brainstorming` → `writing-plans` → `subagent-driven-development`. Dispatch implementer/review subagents on **Opus** (`model: opus`) — the user explicitly wants Opus, no cheaper models. Strict **TDD** (test fails first), one commit per task, then `finishing-a-development-branch` → merge to `main`. One feature branch per milestone.

**Design invariants:** LLM never in the real-time loop; the **validation gate is authoritative**; **abort preempts** any in-flight command; model-agnostic via OpenRouter (OpenAI-compatible) with **constrained JSON output, not tool-calling**, validated by `flight_safety.models.parse_command` (single schema source of truth), retry once on invalid.

**Operational gotchas (learned the hard way):**
- **`pkill -x mavsdk_server`** — use exact-name match. **Never `pkill -f mavsdk_server`**: `-f` matches your own shell's command line (it contains the string) and kills your shell (exit 144, no output).
- MAVSDK here reports `battery.remaining_percent` on a **0–100** scale → normalized to 0–1 in `bridge.read_telemetry`.
- MAVSDK connect string: **`udpin://0.0.0.0:14540`** (PX4 SITL offboard port).
- Each `FlightBridge` spawns its own `mavsdk_server` on 14540 → two can't run at once. Integration tests use a **shared module-scoped fixture**; `bridge.close()` stops the server.
- **Secrets live in `.env` (gitignored)**: `AS_OPENROUTER_API_KEY`, `AS_MODEL`, `FS_GEOFENCE`. **NEVER put a real key in `.env.example` (it is git-tracked).** The geofence must contain the SITL home (~47.398, 8.546) or commands get rejected as out-of-bounds. M3 adds `VB_TOPIC` (gz camera topic) and optional `DASH_*` / `VB_*` overrides (defaults are fine locally).
- **M3 three-process layout + ports:** flight-safety ws **:8765**, video bridge MJPEG/health **:8082**, dashboard (serves built UI + browser ws) **:8080**. The browser `<img>` hits the video bridge directly; if the bridge is down/unhealthy the dashboard auto-falls back to a **Three.js telemetry scene** (never a dead pane). The dashboard reuses `assistant.Agent` + the **demuxing `SafetyClient`** (one ws carries telemetry pushes [no `id`] + id-correlated command replies). Browser-facing hub guards `handle_*` so a dead safety link surfaces as a narration, not a dropped socket.
- **M3 video bridge (gz):** set `VB_TOPIC` to the camera image topic; confirm the exact topic name + `gz.transport*/gz.msgs*` binding versions via the **camera spike** (`src/video_bridge/source.py` imports them lazily and degrades to "no frames" if absent). `on_image` assumes tightly-packed pixels — handle `msg.step` row stride if the spike shows padded rows (TODO marker in source). `frontend/dist` is gitignored; run `npm --prefix frontend run build` before `python -m dashboard` serves the UI.
- **M3 camera spike (T1) — DONE (2026-06-09, validated live).** Airframe `make px4_sitl gz_x500_mono_cam`; image topic is **`/world/default/model/x500_mono_cam_0/link/camera_link/sensor/camera/image`** (set `VB_TOPIC` to this). Headless EGL **does** render frames on the GTX 970: **1280×960, `step=3840 = width*3` → RGB, tightly packed (no row padding)**, so the `on_image` stride TODO is confirmed unnecessary and `channels=3` is correct. gz binding versions: **gz.transport13 13.5.0 / gz.msgs10 10.3.2 / gz sim 8.12.0** (Harmonic).
- **M3 gotcha — gz Python bindings live ONLY in the system Python (3.12), not the 3.11 project venv** (the `.so` are `cpython-312` ABI). Run the video bridge under the system interpreter: `PYTHONPATH=src VB_TOPIC=... VB_PORT=... /usr/bin/python3 -m video_bridge` (system python3 already has fastapi/uvicorn/Pillow/pydantic-settings). flight_safety + dashboard run under the project venv as normal.
- **M3 gotcha — default ports 8080/8082 are taken on this box** by an unrelated 24/7 "AMP" panel. For local runs use `DASH_PORT=8090` and `VB_PORT=8092` (flight-safety 8765 is free). When the browser is remote/containerized (e.g. the Playwright MCP browser), `127.0.0.1` is NOT the host — set `DASH_VIDEO_STREAM_URL=http://<host-LAN-IP>:<VB_PORT>/stream.mjpg` so the `<img>` is reachable; `DASH_VIDEO_HEALTH_URL` can stay `127.0.0.1` (polled server-side).
- **M3 gotcha — resource ceiling on the 4GB GTX 970.** Running the camera SITL (1280×960 EGL render) + video bridge (JPEG encode ~20fps) + a headless Chromium + the other services together HARD-LOCKED the machine (full reboot). The code is fine; the box is the limit. For e2e, lighten the load: lower the camera sensor resolution in the model SDF and/or drop the bridge frame rate (`frame_interval_s`) / `VB_JPEG_QUALITY`, run one heavy consumer at a time, and avoid the headless browser + SITL simultaneously if possible. **Done (2026-06-09):** `PX4-Autopilot/Tools/simulation/gz/models/mono_cam/model.sdf` camera is now **640×480 @ 10 Hz**. With this + `VB_JPEG_QUALITY=60` the full stack ran at load ~1.5 (vs the lock-up at full res) and `pytest -m integration` passed. Note the SDF edit lives in the PX4 repo, not this project. **To restore PX4's original full-res camera**, set that file's `<image>` back to `<width>1280</width><height>960</height>` and `<update_rate>30</update_rate>` (the original values).
- **⚠️ SITL log bloat (learned the hard way 2026-06-09):** PX4's interactive `pxh>` console prints an endless prompt stream to stdout. **Never redirect a backgrounded `make px4_sitl` to a plain file** — it grew `/tmp/m3-e2e/sitl.log` to **37 GB** and nearly filled the disk. If you must background SITL, discard its console (`>/dev/null 2>&1`) or use `PX4_RUN_DEFAULT_CONSOLE=0` / a `head -c`-capped pipe. Foreground terminals (as in *How to run*) are fine. Always `rm` any captured SITL log when done.
- **M3 arm anomaly — RESOLVED (2026-06-09).** The earlier one-off "armed at ~10 m after only a `loiter`" did **not** recur on a clean run: with a clean baseline (no GCS on 14550), after a full loiter cycle the vehicle stayed `armed=False, HOLD, grounded` and PX4 logged **0** arm events. It was an artifact of the overloaded/rebooting box, not a code defect (actuation paths re-verified read-only; arm only via `ArmTakeoffCommand` through the gate).
- **Cockpit v2 camera-test world:** a dedicated **`PX4-Autopilot/Tools/simulation/gz/worlds/cam_test.sdf`** (default world + colorful landmark pillars/sphere/tower/landing-pad, sky-blue + green ground) gives the FPV feed something to look at. - **Cockpit v2 manual control:** `take_control` enters **OFFBOARD** (requires armed + airborne — "take off first" else), browser streams `{"type":"manual",forward,right,down,yaw_rate}` (body FRD, ≤20 Hz) → gate clamps to `max_speed_ms`/`max_yaw_rate_dps` + **geofence brake** (zeros horizontal if the 1 s look-ahead exits the fence) → dispatcher's 20 Hz OFFBOARD loop pushes setpoints; a **500 ms watchdog** decays a stale setpoint to zero (hover) so a dropped browser can't fly away. `release_control`/ABORT → `handback()` (OFFBOARD off → HOLD). Keyboard: WASD move, Q/E yaw, R/F alt, Shift boost. The dashboard owns `control_state` and pushes it on change + connect.
- **Cockpit v2 streaming chat:** the model emits one prose sentence (the human-facing `say`) THEN the JSON command; `command_gen.propose_stream` streams the prose as `chat_delta` reply tokens (and `reasoning_content` as "thinking" when the model exposes it), suppresses the JSON from the stream, then parses it. `takeover`/`handback` were removed from the LLM verb vocabulary (now driven by the UI toggle). Latency cut by reusing the last pushed telemetry instead of a fresh `get_telemetry`.

PX4 build deps are in a dedicated **`/hey/projects/px4-build-venv`** (PX4's `ubuntu.sh` doesn't recognize Mint, and the base python is uv-managed/PEP-668-locked). The integrity dataset path is `__file__`-anchored so it runs from any CWD. Live runs need `AS_OPENROUTER_API_KEY`; per-case API errors are recorded as failed cases (one flaky call won't void a benchmark). Scoring is structural (golden verb/params within tolerance) + gate verdict — **no LLM-judge** in v1.

## Key decisions log
- Architecture: **two services (Approach B)** — LLM walled off behind the validated safety API.
- First vertical slice: **NL command & control with shared/hand-off control**.
- Interface: **CLI for M2**, web dashboard for M3 (FPV is video-centric).
- Telemetry: **snapshot-on-demand** in M2 (`get_telemetry`); **real-time push stream** added in M3 (periodic `{"type":"telemetry"}` frames, id-less; demuxed client-side).
- Model: model-agnostic; OpenRouter at the start (DeepSeek tested live and worked through the validate+retry path).
- M3 video: **real gz camera over MJPEG** via a **standalone video-bridge process** (Approach 2 — crash isolation) with a **Three.js telemetry-driven fallback** if the camera/EGL is unavailable. Frontend: **Vite + React + react-three-fiber**, **Layout B** (ground-station split). Browser talks only to the dashboard backend (control/telemetry) + the video bridge (MJPEG `<img>`); the safety service stays walled off.
- Cockpit v2: **manual flight via gate-validated OFFBOARD** (browser never drives the vehicle directly — every velocity setpoint passes the deterministic gate: clamp + geofence brake + hover watchdog), keeping the safety invariant intact while finally making `takeover`/`handback` real. **MANUAL⇄ASSISTANT toggle** (dashboard-owned `control_state`) with ABORT as a separate emergency. **Streaming chat** kept **unified** in the dashboard backend (no separate port — async I/O doesn't block telemetry/setpoint fan-out). Frontend rebuilt as an **immersive FPV/OSD cockpit** (full-bleed video + telemetry-driven overlays) on a small theme/design-system; keyboard-only manual input this round (joysticks/gamepad deferred).
